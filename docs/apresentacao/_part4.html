Diagrama de classes

As classes saem dos substantivos dos casos de uso (série, carga, exercício, treino, foto) e levam o mesmo nome no diagrama e no código.

Uma decisão por entidade. É ela que define quem manda quando as duas cópias discordam.

Entidade-relacionamento — SQLite local

Duas tabelas, nenhuma relação entre si e nenhuma coluna de usuário: o aparelho só guarda dados de quem está logado nele.

Entidade-relacionamento — Supabase / Postgres

Estruturalmente equivalente ao local nas tabelas de domínio, sem a coluna de fila: ela é conceito só do aparelho.

Row Level Security

O app usa apenas a chave anônima. Quem decide o que cada sessão enxerga é o banco, não o cliente — e o gateway ainda filtra por dono, como defesa em profundidade.

Tabela / bucketRegra
set_logsauth.uid() = user_id em select, insert, update e delete
progress_photosauth.uid() = user_id em select, insert, update e delete
body_assessmentsauth.uid() = user_id em select, insert, update e delete
nutrition_plansauth.uid() = user_id — sem update, porque o plano não é editado
storage progress-photos(storage.foldername(name))[1] = auth.uid()::text
storage assessmentsidem: bucket privado, com acesso por URL assinada
  • Nenhuma chave service_role no aplicativo. O bundle de um app mobile é inspecionável; só a chave anônima entra nele, e ela sozinha não lê nada sem uma sessão válida.
  • Defesa em profundidade no delete. Além da política de RLS, o gateway de sincronização filtra a remoção pelos ids e pelo dono — um teste dedicado garante que as duas condições continuam lá.
  • Sessão nunca em texto puro. O token é cifrado em AES-256 com a chave guardada no Keychain (iOS) ou Keystore (Android), porque a sessão do Supabase passa dos 2 KB que o armazenamento seguro puro aceita.
  • A posição do usuário não é dado persistido. Ela é lida, usada para ordenar academias e descartada — não há linha, coluna nem bucket onde ela pudesse vazar.
